# Harry Potter Card Game Analytics Dashboard

A Vue 3-based analytics dashboard for tracking character (Reverberation, Echo) performance metrics in Harry Potter: Magic Awakened. The application visualizes win rates, attendance rates, and statistical distributions across different game modes.

## 🚀 Recent Optimizations

- **Aggregated Data Loading**: All archive snapshots are collapsed into a single compact `trends.json` (~18KB gzipped, one request) instead of fetching every archive file — first-load data payload cut ~99%
- **Mobile Responsive**: Fully optimized for mobile and tablet devices with adaptive layouts
- **Performance**: Chart.js optimizations with reduced animation complexity and improved rendering
- **Image Loading**: WebP format support with automatic fallback to PNG, plus preloading strategy
- **User Experience**: Loading states and error handling with retry functionality

## 📄 Pages

- `/` — front page: paper masthead, this week's ink plate, movers column and the five sections
- `/analytics` — full echo analytics (scatter, standings, trends, detailed table)
- `/cards` — Card Codex; `/cards/:id` — one card page
- `/echoes` — all 19 player echoes; `/echoes/:id` — one echo page (stats, rarity variants, card synergies)
- `/sales-optimizer` — Sales Optimizer
- `/quiz` — Magic Quiz
- `/resources` — the library of external tools

## 📊 Features

- **Front page**: a paper masthead over this week's ink plate (top win rate, most picked, biggest jump, 19-echo scatter), a week-over-week movers column and a five-row contents index, switchable between all four brackets
- **Interactive Scatter Charts**: Visualize character performance by plotting attendance rate vs win rate
- **Trend Analysis**: Track win rate and attendance rate trends over time with line charts
- **Filterable Data**: Filter data by:
  - Character (Reverberation) selection
  - Game mode (1v1 or 2v2, low or high rank brackets)
  - Time periods
- **Comprehensive Data Tables**: Detailed statistics with sortable columns
- **Real-time Analytics**: Dynamic chart updates based on selected filters
- **Character Data**: Complete mapping of 19 Harry Potter characters with avatar images
- **Global Search**: A header overlay across all 141 cards, 19 echoes and 1,847 quiz questions — press `/` or `Ctrl/Cmd+K`; the index is fetched on first open, never on page load

## 🚀 Getting Started

### Prerequisites

- Node.js ^20.19.0 or >=22.12.0
- npm (comes with Node.js)

### Installation

1. Clone the repository:

```bash
git clone <repository-url>
cd gl-hpma-phb
```

2. Install dependencies:

```bash
npm install
```

### Development

Run the development server:

```bash
npm run dev
```

The application will be available at `http://localhost:5173` (or another port if 5173 is in use).

### Build for Production

Create an optimized SPA build (fast, no prerender):

```bash
npm run build
```

Create the deployable build with static HTML for every indexable route
(requires Chrome/Chromium; Puppeteer downloads one on CI/Netlify):

```bash
npm run build:prerender
```

`build:prerender` runs `vite build`, then `scripts/prerender.mjs` writes 167
static pages (`/`, `/analytics`, `/cards`, `/cards/:id` × 141, `/echoes`,
`/echoes/:id` × 19, `/quiz`, `/sales-optimizer`, `/resources`) into `dist/`.
Each page carries its per-entity bilingual title/description, canonical and OG
tags; `dist/sitemap.xml` is generated from the same data (167 URLs). Netlify
uses this command (`netlify.toml`).

Verify the prerendered output:

```bash
npm run verify:prerender
```

`verify:prerender` is a dependency-free Node check over the built `dist/`: it
requires exactly 167 pages (7 index pages, 141 cards, 19 deck echoes), 167
sitemap URLs that each resolve to a page file, exactly one canonical link per
page pointing at that page's URL, detail titles that contain the entity name,
and no `Loading card…` / `Loading echo…` placeholders. It exits non-zero and
lists every failure. Run it after `npm run build:prerender`; the 167-page
contract lives in `scripts/verify-prerender.mjs` and must be updated when the
spellbook or echoes module changes the entity counts.

The `Prerender gate` workflow (`.github/workflows/prerender.yml`) runs
`npm run build:prerender`, then `npm run verify:prerender`, nightly, on every
push to `main`, and on demand via `workflow_dispatch`. Pull-request CI
(`ci.yml`) stays Chrome-free and fast: it runs the unit tests and the plain
`npm run build` without the prerender pass.

### Preview Production Build

Preview the production build locally:

```bash
npm run preview
```

### Global Search Index

The header's search overlay reads one build-time index generated from the
committed data modules:

```bash
npm run build:search-index
```

`scripts/build-search-index.mjs` writes `public/search-index.json` with one
entry per card (141), player-visible echo (19) and quiz question (1,847). Each
entry is `{ id, name, aliases, type, url }`; rich-text markup is stripped and
the payload is ~118 KB gzipped (budget: under 150 KB). The generated file is
gitignored — the `predev`, `prebuild` and `prebuild:prerender` npm hooks rebuild
it, so `npm run dev`, `npm run build` and `npm run build:prerender` never ship a
stale index.

The client ([`src/services/searchService.js`](src/services/searchService.js))
fetches the index lazily: the first page load makes no request for it. Opening
the overlay fetches `/search-index.json` once and keeps it in memory for the
session. Queries are tokenized and matched against names and aliases (cards'
Chinese names, echoes' Chinese names, quiz stems in both languages), grouped as
Cards / Echoes / Questions and capped at six results per group. Enter opens the
canonical `/cards/:id`, `/echoes/:id` or `/quiz?bank=…&question=…` URL; there is
no `/search` route, so no new prerendered pages or sitemap entries.

Keyboard: `/` or `Ctrl/Cmd+K` opens (both are ignored while focus is in an
input, textarea, select or contenteditable), `↑`/`↓` move the active row,
`Enter` opens it, `Esc` closes, and `Tab` stays inside the dialog. Focus returns
to the header trigger when the overlay closes without navigating.

### Spellbook Data Updates

Spellbook data is split into two independent modules in [hpma-spellbook](https://github.com/hpma-bits/hpma-spellbook):

- **cards** (`cards-v*`) → `public/data/spellbook/` (`cards.json` + `manifest.json` + `version.json`)
- **echoes** (`echoes-v*`) → `public/data/echoes/` (`echoes.json` + `manifest.json` + `version.json`)

The scheduled `Spellbook Data Update` workflow (Mondays 03:00 UTC) runs:

```bash
node scripts/fetch-spellbook-modules.mjs update
```

It fetches both modules' latest releases, audits `cards.json` / `echoes.json` + `manifest.json` against each module's `checksums.txt`, writes the local `version.json` with an `imageBase` pinned to the release tag, and syncs the `/cardimg/*` / `/echoimg/*` proxy tags in `netlify.toml`. `--check` exits 2 when either module is newer; `--verify` audits the committed data.

Card and echo images are hot-linked from `raw.githubusercontent.com` at the pinned tag. The same-origin `/cardimg/*` and `/echoimg/*` Netlify redirects are the fallback for clients that cannot reach GitHub directly.

### Echo image loading

`/echoes` and `/echoes/:id` render every image through
[`src/components/EchoImage.vue`](src/components/EchoImage.vue). Each image walks
this chain: L1 WebP → L1 PNG → same-origin `/echoimg/<path>` (the Netlify
redirect above) → the local avatar of the 19 tracked deck characters
(`public/images/avatars/echoNN.webp`) → an initial-letter placeholder. The
component owns a fixed box (72 px list avatar / 168 px detail hero / 96 px rarity
variant), so a failed stage never shifts layout; the detail hero is `eager` with
`fetchpriority="high"`, while list and variant images are `lazy` with
`decoding="async"`. Image hosts stay in
`public/data/echoes/version.json` (`imageBase`, `imagesWebp`); no component
hardcodes a CDN domain.

**raw vs fastly.jsdelivr.net measurement (2026-10-24, Shanghai workstation).**
One 32 KB PNG (`images/icon_huixiang_hemin_001.png`) and its 7 KB WebP copy,
three runs each, with:

```bash
curl.exe -sSL --max-time 20 -o NUL \
  -w "http=%{http_code} total=%{time_total}s redirects=%{num_redirects}\n" <url>
```

The proxied runs add `-x http://127.0.0.1:7890`.

| source      | direct                             | via 127.0.0.1:7890      | notes                      |
| ----------- | ---------------------------------- | ----------------------- | -------------------------- |
| raw PNG     | 0.499 / 0.879 / 2.529 s            | 2.581 / 3.120 / 5.836 s | HTTP 200                   |
| raw WebP    | 1.000 / 1.095 / 20.019 s (timeout) | 5.350 / 5.643 / 6.159 s | HTTP 200, one 20 s timeout |
| fastly PNG  | 1.700 / 1.733 / 1.892 s            | 1.682 / 1.777 / 3.132 s | direct 301 → raw           |
| fastly WebP | 0.624 / 0.748 / 2.082 s            | 1.659 / 3.681 / 9.252 s | direct 301 → raw           |

Direct `fastly.jsdelivr.net` answered with a 301 to the identical
`raw.githubusercontent.com` object, so it cannot beat raw from this network — it
only adds a round trip. Raw won on median (PNG 0.88 s, WebP 1.10 s) and serves
without a redirect; `/echoimg` stays the client fallback for networks where raw
is unreachable. **Final choice: keep the raw imageBase** (no data change). A
side check of `cdn.jsdelivr.net` returned HTTP 200 directly in 0.81–1.35 s with
no redirect; it is a candidate for the next data-update probe, but not adopted
here because the issue benchmarked fastly and raw still had the lower median. If
a future probe flips the order, change only
`public/data/echoes/version.json` → `imageBase` (or the generating script),
never a component.

Quiz data (`public/data/quiz/`) follows the same pipeline from [hpma-quizbank](https://github.com/hpma-bits/hpma-quizbank) releases: the scheduled `Quiz Data Update` workflow (Mondays 03:30 UTC, staggered half an hour after spellbook) pulls the new tag, commits it → the push triggers the Netlify deploy. To pull immediately, trigger the workflow from the Actions tab (`workflow_dispatch`) or run locally:

```bash
node scripts/fetch-quiz.mjs update
```

## 🎮 Game Modes

The dashboard supports four game modes:

- **1v1 Low**: 1v1 matches with ratings below 7500
- **1v1 High**: 1v1 matches with ratings 7500 and above
- **2v2 Low**: 2v2 matches with ratings below 7500
- **2v2 High**: 2v2 matches with ratings 7500 and above

## 📈 Key Metrics

- **Win Rate**: Percentage of matches won with a character in a given period
- **Attendance Rate**: Percentage of matches a character was used in a given period
- **Pick Rate**: Number of times a character was selected
- **Ban Rate**: Number of times a character was banned

## 💾 Data Storage

- Raw data snapshots are stored in the repo-root `archive/` directory (crawler output and build input, **not** deployed with the site)
- Data files include timestamps for version tracking
- Current working data is in `snapshot.json`
- The client reads only `public/archive/trends.json` (served at `/archive/trends.json`), a compact aggregate ([period, echo, mode, winrate, pickrate] rows) built from all snapshots in `archive/` with `npm run build:trends`; the crawler workflow regenerates it automatically on every new snapshot (`npm run verify:trends` re-checks it against the raw archives)
- Raw archive files are kept as the source of truth and download archive, but are no longer fetched by the app
